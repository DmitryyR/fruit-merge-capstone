# Матриця доказів

Стан на 03.10.2026: підготовлені лише документи. Жодних тестових прогонів гри, реалізаційних комітів, незалежного code review, відео або PR ще немає. Шляхи в кодових лапках — заплановані артефакти, не готові докази.

| Практика | Конкретний запланований доказ | Коли | Поточний статус |
|---|---|---|---|
| Контекст-інженерія | [AGENTS.md](../../AGENTS.md) + його commit + запис конкретного застосування правила, наприклад збережений red замість послаблення тесту; динамічний контекст — реальний diff і test output у журналі задачі | T0, T1 і далі | Правила створено; застосування під час кодування ще не доведено |
| SDD | [Вимоги](../requirements.md), [дизайн](../design.md), [план](../plan.md); документаційний SHA раніше першого code SHA; зміни специфікації з причиною, якщо вони виникли | T0 та при змінах | Файли створено; погодження і commits попереду |
| Верифікація / TDD | `tests/unit/merge.test.ts`, raw `T1-red.log`/`T1-green.log`, revision або patch кожного; `scripts/check.mjs`; final-check log/CI URL та code SHA | T1–T5 | Заплановано |
| Loop engineering | Один запит на етап + фактична послідовність test output → агентська правка → повторний run; `docs/evidence/runs/T2-loop.md`, число раундів і причина зупинки | T2 або інший етап із реальними ітераціями | Умовно заплановано; check без агентських ітерацій недостатній |
| Maker ≠ checker | `docs/reviews/<reviewed-sha>.md`: окремий рецензент/прохід, scope, SHA, знахідки або їх відсутність; відповіді й fix commits | T5 | Заплановано; спосіб checker погоджується |

Журнал рівнів довіри як окрему практику наразі не заявляємо. Межі делегування і реальні рішення збережемо в `docs/decisions.md` та робочих журналах. Якщо згодом користувач обере повний autonomy log, додамо його лише з фактичними записами.

Project Factory не плануємо й не позначатимемо в PR. Наявність кількох skills або AGENTS.md не дорівнює застосуванню Project Factory.

## Формат майбутнього журналу

Кожен запис: ID задачі/вимоги; дата з часовим поясом; вхідний запит; роль; команда; commit SHA; clean/dirty; patch для незакомічених змін; exit code; посилання на raw output; висновок/наступна дія. Без секретів і сторонніх даних. Стани: planned → captured → verified; failed і not run зберігаються явно.

Не створювати порожні log/review файли для видимості виконання. Не фабрикувати red, «знайдений баг» або втручання людини. Контроль із навмисно неправильним assertion позначати саме контрольним експериментом.

## Інші обов'язкові докази здачі

| Результат | Артефакт | Статус |
|---|---|---|
| Працездатний продукт | README, код, fresh-checkout run, `docs/qa/acceptance-report.md` | Заплановано |
| Власні рішення учасника | `docs/decisions.md`, фактичне погодження/зміни; відповідний розділ PR | Заплановано |
| Відео 60–120 секунд | Відкриваний без логіну URL, перевірена тривалість | Заплановано |
| PR | Реальний GitHub URL, правильні base/head, повний шаблон | Заплановано |
| Навчальна платформа | Збережений клікабельний PR URL і підтвердження подання | Заплановано; потрібні URL завдання або скриншот поля |

У фінальному PR замінити майбутні шляхи на перевірені GitHub permalinks чи CI URLs. Галочки ставити тільки для captured/verified практик, не для плану.
